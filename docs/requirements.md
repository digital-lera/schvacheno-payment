# Requirements.md: Требования к системе обработки платежей (Схвачено)

## Общая информация
**Версия**: 1.0  
**Дата**: 08.01.2026  
**Сфера**: Финтех (микросервисная система платежей с distributed sagas)  
**Технологии**: .NET 9, PostgreSQL/EF Core, Kafka, Redis, gRPC, Docker  

### 1. Инициирование платежа
```
Функция: Инициирование платежа
  Как пользователь
  Я хочу отправить запрос на платеж с карты
  Для того, чтобы получить уникальный transactionId и статус обработки
  
  Сценарий: Успешное инициирование платежа
    Дано пользователь с балансом > суммы платежа
    Когда отправлен POST /pay/initiate с данными {userId, amount: 1000, currency: "RUB", cardken}
    То возвращается 202 Accepted с transactionId
    И в Kafka публикуется событие "PaymentRequested"
    И в PostgreSQL создается запись Transactions со статусом "Initiated"
```

### 2. Проверка статуса платежа
```
Функция: Проверка статуса транзакции
  Как пользователь
  Я хочу узнать текущий статус моего платежа
  Для того, чтобы отобразить пользователю прогресс
  
  Сценарий: Получение статуса Initiated
    Дано существует транзакция с transactionId
    Когда GET /pay/status/{transactionId}
    То возвращается статус "Initiated" с pollingInterval: 2000ms
```

### 3. Обработка лимитов пользователя
```
Функция: Контроль дневных лимитов
  Как система
  Я хочу проверять дневной лимит пользователя
  Для того, чтобы предотвратить превышение 100k RUB/день
  
  Сценарий: Превышение дневного лимита
    Дано пользователь потратил 90k RUB сегодня
    Когда инициируется платеж на 20k RUB
    То возвращается 402 PaymentRequired
    И логируется событие "LimitExceeded"
```

### 4. Конвертация валют
```
Функция: Конвертация валют по курсу ЦБ РФ
  Как система
  Я хочу конвертировать RUB <-> USD/EUR
  Для того, чтобы поддерживать мультивалютные платежи
  
  Сценарий: Конвертация с кэшем в Redis
    Дано курс USD/RUB = 95.5 кэширован в Redis
    Когда платеж 100 USD -> RUB
    То amount конвертируется в 9550 RUB
    И при недоступности API используется fallback-курс
```

### 5. Saga: Отправка уведомлений
```
Функция: Асинхронные уведомления
  Как система
  Я хочу отправить email/SMS после успешного платежа
  Для того, чтобы пользователь получил подтверждение
  
  Сценарий: Успешная отправка уведомления
    Дано Kafka сообщение "PaymentProcessed"
    Когда Notifications consumer обрабатывает событие
    То отправляется email via SendGrid
    И статус обновляется на "Completed"
    
  Сценарий: Fail уведомления с compensating transaction
    Дано SendGrid API недоступен
    Когда Notifications consumer падает
    То сообщение уходит в DLQ Kafka
    И saga инициирует PaymentRefund
```

### 6. Безопасность и idempotency
```
Функция: Защита от дублирования платежей
  Как система
  Я хочу игнорировать повторные запросы с тем же transactionId
  Для того, чтобы избежать double charging
  
  Сценарий: Idempotent запрос
    Дано платеж с transactionId уже обработан
    Когда повторный POST /pay/initiate с тем же transactionId
    То возвращается 200 OK с текущим статусом
```

### 7. Аудит и логирование
```
Функция: Аудит всех транзакций
  Как администратор
  Я хочу видеть полную историю всех операций
  Для того, чтобы провести расследование инцидентов
  
  Сценарий: Логирование критических событий
    Дано любой платеж/ошибка
    Когда происходит событие
    То Serilog пишет в PostgreSQL AuditLog с UserId, IP, Timestamp, Action
```

## Non-Functional Requirements
- **Performance**: < 200ms p95 для /pay/initiate
- **Availability**: 99.9% uptime (Docker Compose + healthchecks)
- **Scalability**: Horizontal scaling Payments service
- **Security**: JWT auth, card data encryption (Data Protection API)
- **Moniring**: OpenTelemetry metrics + Grafana dashboard
